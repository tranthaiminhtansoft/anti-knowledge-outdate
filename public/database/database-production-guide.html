Không phải hai thế giới tách biệt

Production thường phối hợp nhiều datastore theo workload.

Giống nhau

  • Đều cần index, backup, security
  • Đều có replication và failure
  • Đều phải đo latency, capacity

SQL nổi bật

  • JOIN và constraint
  • Transaction đa bản ghi
  • Strong consistency mặc định

NoSQL nổi bật

  • Scale ngang theo partition key
  • Access pattern cụ thể
  • Consistency có thể đánh đổi

Củng cố

Payment và cart nên dùng cùng một database không?
Không bắt buộc. Payment thường cần transaction mạnh; cart có thể ưu tiên throughput và availability.
NoSQL có luôn tự scale không?
Không. Chỉ distributed/managed database đã cấu hình autoscaling mới thêm capacity tự động.
Read replica có tăng năng lực ghi SQL không?
Không. Replica chủ yếu chia tải đọc và hỗ trợ HA; write vẫn đi vào Primary.
PHẦN 02

Data Design & Query Performance

Cùng dữ liệu payment, SQL tổ chức quan hệ linh hoạt; NoSQL tối ưu document theo đường đọc đã biết.

Cùng màn hình “Payment history”

Hai data model, cùng mục tiêu trả kết quả nhanh và đúng.

Giống nhau

  • Thiết kế từ query quan trọng
  • Index đúng key và sort
  • Tránh đọc thừa, N+1

SQL

  • users → orders → payments
  • JOIN và foreign key
  • Normalize; denormalize có chọn lọc

NoSQL

  • payment-history document
  • Embed dữ liệu cần đọc cùng lúc
  • Tránh fan-out và hot partition

Chưa tạo index — Full scan

Query giữ nguyên; database chỉ có thêm cấu trúc để tìm và sắp xếp theo access pattern này. Planner chọn index theo engine, statistics, selectivity và cost.

SELECT * FROM payment_history
WHERE user_id = $1 AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 12;
CREATE INDEX idx_payment_history_user_status_created_at
ON payment_history (user_id, status, created_at DESC);
Demo giả định dữ liệu có selectivity phù hợp. Xác minh production bằng EXPLAIN (ANALYZE, BUFFERS).
Đang kiểm tra từng record.

Củng cố

Schema linh hoạt có nghĩa không cần thiết kế trước?
Không. NoSQL càng phụ thuộc access pattern và partition key; thiết kế sai dễ tạo fan-out/hot key.
Index có làm mọi query nhanh hơn không?
Không. Nó phải khớp filter/sort và làm tăng chi phí write, storage.
Khi nào denormalize?
Khi một đường đọc quan trọng cần tránh JOIN/fan-out và bạn chấp nhận chi phí đồng bộ dữ liệu trùng.
PHẦN 03

Data Correctness & Reliability

SQL và NoSQL đều phải chống ghi trùng, race condition và lỗi giữa nhiều hệ thống—nhưng dùng cơ chế khác nhau.

SQLTransaction, isolation, row lock.
NoSQLAtomic document, conditional write.
Dùng chungIdempotency, unique key, retry.

Giống nhau

  • Idempotency key + unique constraint
  • Retry có backoff
  • Business invariant phải kiểm chứng

SQL

  • SELECT … FOR UPDATE
  • Isolation + transaction
  • Constraint là lớp cuối

NoSQL

  • Conditional write / compare-and-set
  • Atomic trong một document/key
  • Transaction đa key tùy sản phẩm
Dual-write: DB commit nhưng publish event lỗi → dùng Transactional Outbox/CDC; không giải bằng “retry đại”.

Củng cố

Transaction có tự ngăn mọi race condition?
Không. Phải chọn isolation/câu lệnh đúng; có thể cần lock, version hoặc atomic update.
NoSQL có transaction không?
Nhiều sản phẩm có, nhưng phạm vi và chi phí khác nhau. Thiết kế thường ưu tiên atomicity trong một key/document.
Client retry POST /payment có tạo giao dịch trùng không?
Có thể. Idempotency key kết hợp unique constraint giúp cùng yêu cầu trả lại cùng kết quả.

Củng cố

Replication có thay thế backup không?
Không. Replication phục vụ HA; backup/PITR phục hồi sau xóa sai, corruption hoặc mất cả cluster.
Backup thành công có đủ chưa?
Chưa. Phải restore vào môi trường cô lập, verify dữ liệu và đo đạt RPO/RTO.
Scale API có thể làm database chết nhanh hơn vì sao?
Mỗi pod mở connection pool riêng. Tổng connection và concurrency có thể vượt khả năng database.
